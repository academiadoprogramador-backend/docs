## Injeção de Dependência no ASP.NET MVC

Nas aulas anteriores, construímos uma aplicação com:

- Controllers;
- Views;
- ViewModels;
- TagHelpers;
- repositórios;
- persistência dos dados em arquivo JSON.

Com isso, já conseguimos organizar várias responsabilidades da aplicação.

Porém, ainda existe uma pergunta importante:

> quem deve criar os objetos utilizados pelo Controller?

Imagine que o `FornecedorController` precise utilizar um repositório.

Uma primeira solução seria criar o contexto e o repositório dentro do próprio Controller.

Essa solução funciona.

Mas, conforme a aplicação cresce, os Controllers passam a conhecer muitos detalhes de criação dos objetos.

Para evitar esse acoplamento, podemos utilizar **injeção de dependência**.

## O problema de criar dependências manualmente

Uma dependência é um objeto que outra classe precisa utilizar para realizar seu trabalho.

Por exemplo, o Controller de fornecedores precisa de um repositório para:

- buscar fornecedores;
- cadastrar fornecedores;
- editar fornecedores;
- excluir fornecedores.

Nesse caso, o Controller depende de `RepositorioFornecedorEmArquivo`.

Sem injeção de dependência, poderíamos escrever algo assim:

```csharp
public class FornecedorController : Controller
{
    private readonly RepositorioFornecedorEmArquivo repositorio;

    public FornecedorController()
    {
        ContextoJson contexto = new ContextoJson();
        contexto.Carregar();

        repositorio = new RepositorioFornecedorEmArquivo(contexto);
    }
}
```

O Controller agora possui duas responsabilidades:

- atender às requisições da aplicação;
- criar e configurar os objetos necessários para trabalhar.

O problema não está apenas na quantidade de linhas.

O Controller também passa a conhecer detalhes que não pertencem diretamente a ele:

- o tipo concreto do contexto;
- a forma de carregamento dos dados;
- a implementação do repositório;
- a ordem em que os objetos precisam ser criados.

## O que é uma dependência?

Considere uma classe que utiliza outra classe:

```csharp
public class RelatorioController : Controller
{
    private readonly RepositorioRelatorio repositorio;
}
```

O `RelatorioController` não consegue trabalhar sem um `RepositorioRelatorio`.

Por isso, dizemos que `RepositorioRelatorio` é uma dependência do Controller.

Podemos representar essa relação assim:

```text
RelatorioController
    depende de
RepositorioRelatorio
```

O mesmo acontece no projeto de controle de medicamentos:

```text
FornecedorController
    depende de
RepositorioFornecedorEmArquivo
```

E o repositório, por sua vez, depende de:

```text
RepositorioFornecedorEmArquivo
    depende de
ContextoJson
```

Portanto, existe uma cadeia de dependências:

```text
FornecedorController
    -> RepositorioFornecedorEmArquivo
        -> ContextoJson
```

## O que é injeção de dependência?

Injeção de dependência é uma técnica em que um objeto recebe os objetos de que precisa, em vez de criá-los diretamente.

Em vez de o Controller criar o repositório:

```csharp
public FornecedorController()
{
    repositorio = new RepositorioFornecedorEmArquivo(contexto);
}
```

o repositório pode ser recebido pelo construtor:

```csharp
public FornecedorController(RepositorioFornecedorEmArquivo repositorio)
{
    this.repositorio = repositorio;
}
```

Nesse formato, outra parte da aplicação fica responsável por criar o repositório.

O Controller apenas informa do que precisa.

> Injetar uma dependência significa entregar um objeto pronto para a classe que precisa utilizá-lo.

## Injeção pelo construtor

A forma mais comum de injeção no ASP.NET Core é a **injeção pelo construtor**.

Observe um Controller com essa abordagem:

```csharp
public sealed class FornecedorController : Controller
{
    private readonly RepositorioFornecedorEmArquivo repositorio;

    public FornecedorController(RepositorioFornecedorEmArquivo repositorio)
    {
        this.repositorio = repositorio;
    }
}
```

O construtor recebe um `RepositorioFornecedorEmArquivo`.

Depois, o objeto recebido é guardado no campo `repositorio`.

As Actions podem utilizar esse campo normalmente:

```csharp
[HttpGet]
public ActionResult Listar()
{
    List<Fornecedor> fornecedores = repositorio.SelecionarTodos();

    return View(fornecedores);
}
```

O Controller não precisa saber:

- como o repositório foi criado;
- quem criou o `ContextoJson`;
- onde os dados estão armazenados;
- quando o contexto foi carregado.

Ele apenas utiliza o objeto recebido.

## Quem cria os objetos?

Se o Controller não cria o repositório, alguma outra parte precisa realizar esse trabalho.

No ASP.NET Core, essa responsabilidade é realizada pelo **container de injeção de dependência**.

O container é um componente que:

- conhece os serviços registrados na aplicação;
- cria os objetos necessários;
- identifica as dependências de cada objeto;
- entrega esses objetos para os construtores;
- controla o ciclo de vida dos serviços.

Podemos imaginar o container como um catálogo de objetos:

```text
"Quando alguém precisar de ContextoJson,
 crie ou entregue um ContextoJson."

"Quando alguém precisar de
 RepositorioFornecedorEmArquivo,
 crie esse repositório usando ContextoJson."
```

O Controller pede o repositório pelo construtor.

O container verifica como criar o repositório.

Depois, verifica que o repositório precisa de um `ContextoJson`.

Por fim, entrega tudo pronto ao Controller.

## Registrando serviços no Program.cs

Para que o container saiba criar os objetos, precisamos registrá-los.

No projeto de referência, o `Program.cs` contém:

```csharp
WebApplicationBuilder builder = WebApplication.CreateBuilder(args);

builder.Services.AddInfraestruturaEmJson();

builder.Services.AddControllersWithViews();
```

O objeto `builder.Services` representa a coleção de serviços da aplicação.

O método `AddInfraestruturaEmJson` registra os objetos relacionados à persistência em arquivo JSON.

Depois que os registros são feitos, o ASP.NET pode resolver as dependências dos Controllers.

O restante do `Program.cs` continua configurando a aplicação:

```csharp
WebApplication app = builder.Build();

app.UseRouting();
app.MapDefaultControllerRoute();

app.UseStaticFiles();

app.Run();
```

A ideia principal é:

```text
builder.Services
    registra os serviços

builder.Build()
    constrói a aplicação

ASP.NET MVC
    cria os Controllers e injeta suas dependências
```

## Criando um método de extensão para os registros

Poderíamos registrar todos os serviços diretamente no `Program.cs`:

```csharp
builder.Services.AddScoped<ContextoJson>();
builder.Services.AddScoped<RepositorioFornecedorEmArquivo>();
builder.Services.AddScoped<RepositorioMedicamentoEmArquivo>();
```

Isso funcionaria.

Porém, o `Program.cs` começaria a acumular detalhes sobre a infraestrutura de persistência.

Para manter essa configuração organizada, o projeto de referência possui o arquivo:

```text
ControleDeMedicamentos.WebApp/InjecaoDependencia.cs
```

Esse arquivo define a classe `InjecaoDependencia`:

```csharp
public static class InjecaoDependencia
{
    public static void AddInfraestruturaEmJson(this IServiceCollection services)
    {
        // registros dos serviços
    }
}
```

O parâmetro `this IServiceCollection services` transforma o método em um método de extensão.

Assim, podemos chamá-lo desta forma:

```csharp
builder.Services.AddInfraestruturaEmJson();
```

Sem um método de extensão, a chamada precisaria utilizar o nome da classe:

```csharp
InjecaoDependencia.AddInfraestruturaEmJson(builder.Services);
```

O método de extensão deixa a configuração mais natural de ler.

## Registrando o ContextoJson

O primeiro registro do projeto de referência cria o `ContextoJson`:

```csharp
services.AddScoped(_ =>
{
    ContextoJson contexto = new ContextoJson();

    contexto.Carregar();

    return contexto;
});
```

Esse registro informa ao container o que fazer quando algum objeto precisar de um `ContextoJson`.

O código executa as seguintes etapas:

1. cria um novo `ContextoJson`;
2. carrega os dados existentes;
3. retorna o contexto pronto para ser utilizado.

O repositório não precisa chamar `new ContextoJson()`.

Ele apenas recebe o contexto no construtor.

## Registrando os repositórios

Depois de registrar o contexto, registramos os repositórios:

```csharp
services.AddScoped<RepositorioMedicamentoEmArquivo>();
services.AddScoped<RepositorioFornecedorEmArquivo>();
services.AddScoped<RepositorioFuncionarioEmArquivo>();
services.AddScoped<RepositorioPacienteEmArquivo>();
services.AddScoped<RepositorioRequisicaoEntradaEmArquivo>();
services.AddScoped<RepositorioRequisicaoSaidaEmArquivo>();
```

Cada chamada informa ao container que aquele tipo pode ser criado e injetado.

Por exemplo:

```csharp
services.AddScoped<RepositorioFornecedorEmArquivo>();
```

Quando o ASP.NET precisar criar um `FornecedorController`, ele perceberá que o construtor pede um `RepositorioFornecedorEmArquivo`.

Como o tipo foi registrado, o container saberá como criá-lo.

## O repositório recebendo o contexto

O repositório de fornecedores possui um construtor que recebe `ContextoJson`:

```csharp
public class RepositorioFornecedorEmArquivo : RepositorioBaseEmArquivo<Fornecedor>
{
    public RepositorioFornecedorEmArquivo(ContextoJson contexto) : base(contexto)
    {
    }

    protected override List<Fornecedor> ObterRegistros()
    {
        return contexto.Fornecedores;
    }
}
```

O repositório declara sua dependência no construtor.

Ele não precisa conhecer a configuração do container.

Também não precisa saber que o contexto foi carregado a partir de um arquivo JSON.

Essa decisão fica concentrada no registro de infraestrutura.

## Como o container resolve a cadeia

Quando uma requisição precisa acessar `FornecedorController`, o processo pode ser entendido assim:

```text
1. O MVC precisa criar FornecedorController.

2. O construtor pede RepositorioFornecedorEmArquivo.

3. O container encontra o registro do repositório.

4. O construtor do repositório pede ContextoJson.

5. O container cria e carrega ContextoJson.

6. O container cria RepositorioFornecedorEmArquivo.

7. O container entrega o repositório ao Controller.
```

Podemos representar o mesmo fluxo com código:

```text
Program.cs
    registra InjecaoDependencia

InjecaoDependencia
    registra ContextoJson
    registra RepositorioFornecedorEmArquivo

FornecedorController
    recebe RepositorioFornecedorEmArquivo
```

O Controller utiliza a dependência sem criar nenhum desses objetos manualmente.

## Controller completo com injeção

Uma parte do `FornecedorController` da referência pode ser escrita assim:

```csharp
using ControleDeMedicamentos.WebApp.Compartilhado.Arquivos;
using Microsoft.AspNetCore.Mvc;

namespace ControleDeMedicamentos.WebApp.ModuloFornecedores;

public sealed class FornecedorController : Controller
{
    private readonly RepositorioFornecedorEmArquivo repositorio;

    public FornecedorController(RepositorioFornecedorEmArquivo repositorio)
    {
        this.repositorio = repositorio;
    }

    [HttpGet]
    public ActionResult Listar()
    {
        List<Fornecedor> fornecedores = repositorio.SelecionarTodos();

        return View(fornecedores);
    }
}
```

Observe que o Controller não possui:

- `new ContextoJson()`;
- chamada para `contexto.Carregar()`;
- `new RepositorioFornecedorEmArquivo(...)`.

Esses detalhes foram retirados do Controller.

## Um Controller com mais de uma dependência

Alguns Controllers precisam consultar mais de um repositório.

O `MedicamentoController` da referência, por exemplo, precisa de medicamentos e fornecedores:

```csharp
public sealed class MedicamentoController : Controller
{
    private readonly RepositorioMedicamentoEmArquivo repositorioMedicamento;
    private readonly RepositorioFornecedorEmArquivo repositorioFornecedor;

    public MedicamentoController(
        RepositorioMedicamentoEmArquivo repositorioMedicamento,
        RepositorioFornecedorEmArquivo repositorioFornecedor
    )
    {
        this.repositorioMedicamento = repositorioMedicamento;
        this.repositorioFornecedor = repositorioFornecedor;
    }
}
```

Esse Controller precisa do repositório de medicamentos para:

- listar medicamentos;
- cadastrar medicamentos;
- editar medicamentos;
- excluir medicamentos.

Ele precisa do repositório de fornecedores para carregar os fornecedores disponíveis no formulário de medicamento.

O container resolve as duas dependências do construtor.

O Controller não precisa conhecer a ordem de criação dos repositórios.

## O que significa AddScoped?

`AddScoped` registra um serviço com o ciclo de vida **scoped**.

Em uma aplicação web, um escopo normalmente corresponde a uma requisição HTTP.

Isso significa que, durante uma mesma requisição:

- uma instância do serviço pode ser reutilizada;
- Controllers e repositórios podem receber a mesma instância registrada;
- ao final da requisição, o escopo é encerrado.

No projeto de referência, os registros são feitos assim:

```csharp
services.AddScoped<RepositorioFornecedorEmArquivo>();
```

O `ContextoJson` também é registrado como `Scoped`.

Assim, se dois repositórios receberem um `ContextoJson` durante a mesma requisição, eles podem trabalhar com a mesma instância do contexto.

## Outros ciclos de vida

O ASP.NET Core possui outros ciclos de vida comuns.

### Transient

Um serviço `Transient` normalmente recebe uma nova instância cada vez que é solicitado.

```csharp
services.AddTransient<ServicoDeCalculo>();
```

Esse ciclo pode ser adequado para objetos pequenos e sem estado compartilhado.

### Scoped

Um serviço `Scoped` normalmente recebe uma instância por escopo.

Em aplicações MVC, o escopo costuma acompanhar a requisição HTTP.

```csharp
services.AddScoped<RepositorioFornecedorEmArquivo>();
```

Esse é o ciclo utilizado nos repositórios do projeto de referência.

### Singleton

Um serviço `Singleton` utiliza a mesma instância durante toda a execução da aplicação.

```csharp
services.AddSingleton<ConfiguracaoAplicacao>();
```

Ele deve ser usado com cuidado, principalmente quando o objeto possui estado que pode ser alterado por várias requisições.

Podemos resumir os ciclos assim:

```text
Transient
    nova instância a cada solicitação

Scoped
    uma instância por escopo, normalmente uma requisição

Singleton
    uma instância durante toda a aplicação
```

> O ciclo de vida precisa ser escolhido de acordo com o estado e a responsabilidade do serviço.

## Por que o ContextoJson é registrado como Scoped?

O `ContextoJson` contém as coleções utilizadas pela aplicação:

```csharp
public List<Fornecedor> Fornecedores { get; set; } = [];
public List<Medicamento> Medicamentos { get; set; } = [];
public List<Paciente> Pacientes { get; set; } = [];
```

Ele também carrega e salva os dados persistidos.

Ao registrá-lo como `Scoped`, o projeto estabelece uma instância para o escopo atual.

Os repositórios que recebem esse contexto podem utilizar as mesmas coleções durante a requisição.

Isso evita que cada repositório crie um contexto diferente por conta própria.

O registro também concentra a chamada `Carregar()` em um único lugar:

```csharp
services.AddScoped(_ =>
{
    ContextoJson contexto = new ContextoJson();
    contexto.Carregar();

    return contexto;
});
```

## Antes e depois

Sem injeção de dependência, o Controller poderia fazer tudo:

```csharp
public FornecedorController()
{
    ContextoJson contexto = new ContextoJson();
    contexto.Carregar();

    repositorio = new RepositorioFornecedorEmArquivo(contexto);
}
```

Com injeção pelo construtor, ele apenas recebe o que precisa:

```csharp
public FornecedorController(RepositorioFornecedorEmArquivo repositorio)
{
    this.repositorio = repositorio;
}
```

A diferença pode ser resumida assim:

```text
Antes
    Controller cria suas dependências.

Depois
    Container cria as dependências.
    Controller recebe as dependências prontas.
```

## Benefícios da injeção de dependência

Utilizar injeção de dependência ajuda a criar uma aplicação:

- com menos código de criação espalhado;
- com Controllers mais focados nas requisições;
- com configuração de infraestrutura centralizada;
- mais fácil de alterar;
- mais fácil de testar;
- com responsabilidades melhor separadas.

### Menor acoplamento

O Controller deixa de conhecer os detalhes de criação do repositório.

Se a forma de persistência mudar, a configuração pode ser alterada em um local específico.

Por exemplo, o projeto poderia futuramente trocar o armazenamento em JSON por outro tipo de armazenamento.

O Controller continuaria recebendo uma dependência para realizar seu trabalho.

### Configuração centralizada

Os registros ficam reunidos no método:

```csharp
AddInfraestruturaEmJson
```

Isso facilita localizar as decisões relacionadas à infraestrutura.

### Controllers menores

O Controller concentra sua atenção em:

- receber a requisição;
- chamar o repositório;
- preparar a ViewModel;
- retornar a resposta.

Ele não precisa cuidar da montagem da aplicação.

### Testes mais simples

Quando uma dependência é recebida pelo construtor, podemos criar um objeto alternativo para um teste.

Por exemplo, um teste poderia fornecer um repositório preparado com dados conhecidos.

Esse assunto será aprofundado quando estudarmos testes automatizados.

## O container não substitui as responsabilidades

O container cria e entrega objetos.

Ele não deve decidir as regras de negócio da aplicação.

Por exemplo, o container não deve:

- decidir se um medicamento pode ser excluído;
- validar a quantidade do estoque;
- criar uma ViewModel para cada tela;
- substituir uma Action do Controller;
- executar regras que pertencem ao domínio.

Cada parte continua com sua responsabilidade:

```text
Controller
    coordena a requisição

Repositório
    acessa e altera os dados

ContextoJson
    mantém os dados persistidos em JSON

Container de DI
    cria e conecta os objetos

ViewModel
    transporta os dados da tela
```

## Cuidados com a injeção de dependência

Registrar um serviço não significa que ele pode ser utilizado de qualquer maneira.

É importante observar alguns pontos.

### A dependência precisa estar registrada

Se um Controller receber um tipo que não foi registrado e o ASP.NET não conseguir criá-lo, a aplicação apresentará um erro ao tentar construir o Controller.

Por isso, ao adicionar uma dependência, precisamos verificar se ela foi registrada no container.

### O construtor deve declarar o que é necessário

As dependências obrigatórias devem estar visíveis no construtor:

```csharp
public FornecedorController(RepositorioFornecedorEmArquivo repositorio)
{
    this.repositorio = repositorio;
}
```

Isso deixa claro o que o Controller precisa para funcionar.

### Evite criar a mesma dependência manualmente

Depois de registrar um serviço, não é necessário voltar a criá-lo com `new` dentro do Controller.

Misturar as duas abordagens pode gerar configurações duplicadas e dificultar entender qual instância está sendo utilizada.

### Escolha o ciclo de vida com cuidado

Um serviço com estado por requisição normalmente não deve ser registrado como `Singleton` sem uma análise cuidadosa.

Um objeto criado como `Singleton` pode ser compartilhado por várias requisições ao mesmo tempo.

## Estrutura da solução no projeto de referência

Os arquivos envolvidos na injeção de dependência podem ser resumidos assim:

```text
ControleDeMedicamentos.WebApp/
    Program.cs
    InjecaoDependencia.cs
    Compartilhado/
        Arquivos/
            ContextoJson.cs
    ModuloFornecedores/
        FornecedorController.cs
        RepositorioFornecedorEmArquivo.cs
    ModuloMedicamentos/
        MedicamentoController.cs
        RepositorioMedicamentoEmArquivo.cs
```

O fluxo entre esses arquivos é:

```text
Program.cs
    chama AddInfraestruturaEmJson

InjecaoDependencia.cs
    registra ContextoJson e repositórios

ContextoJson.cs
    representa os dados carregados do JSON

RepositorioFornecedorEmArquivo.cs
    recebe ContextoJson

FornecedorController.cs
    recebe RepositorioFornecedorEmArquivo
```

Essa organização separa a configuração da infraestrutura do código das Actions.

## Exemplo completo da configuração

A configuração do projeto de referência pode ser observada neste exemplo:

```csharp
using ControleDeMedicamentos.WebApp.Compartilhado.Arquivos;
using ControleDeMedicamentos.WebApp.ModuloFornecedores;
using ControleDeMedicamentos.WebApp.ModuloFuncionarios;
using ControleDeMedicamentos.WebApp.ModuloMedicamentos;
using ControleDeMedicamentos.WebApp.ModuloPacientes;
using ControleDeMedicamentos.WebApp.ModuloRequisicoes;

public static class InjecaoDependencia
{
    public static void AddInfraestruturaEmJson(this IServiceCollection services)
    {
        services.AddScoped(_ =>
        {
            ContextoJson contexto = new ContextoJson();

            contexto.Carregar();

            return contexto;
        });

        services.AddScoped<RepositorioMedicamentoEmArquivo>();
        services.AddScoped<RepositorioFornecedorEmArquivo>();
        services.AddScoped<RepositorioFuncionarioEmArquivo>();
        services.AddScoped<RepositorioPacienteEmArquivo>();
        services.AddScoped<RepositorioRequisicaoEntradaEmArquivo>();
        services.AddScoped<RepositorioRequisicaoSaidaEmArquivo>();
    }
}
```

E o `Program.cs` utiliza essa configuração:

```csharp
WebApplicationBuilder builder = WebApplication.CreateBuilder(args);

builder.Services.AddInfraestruturaEmJson();
builder.Services.AddControllersWithViews();

WebApplication app = builder.Build();

app.UseRouting();
app.MapDefaultControllerRoute();
app.UseStaticFiles();

app.Run();
```

A partir desse momento, Controllers como `FornecedorController` e `MedicamentoController` podem receber seus repositórios por construtor.

## Conclusão

Injeção de dependência é uma técnica para entregar a uma classe os objetos de que ela precisa.

No ASP.NET Core, o container de injeção de dependência:

- conhece os serviços registrados;
- cria os objetos necessários;
- resolve as dependências entre eles;
- injeta os objetos nos construtores;
- controla seus ciclos de vida.

No projeto de referência, o método `AddInfraestruturaEmJson` registra o `ContextoJson` e os repositórios.

Os Controllers recebem os repositórios pelo construtor.

Assim, a aplicação deixa de criar dependências manualmente dentro dos Controllers.

Podemos resumir a ideia principal assim:

```text
Program.cs
    configura a aplicação

InjecaoDependencia.cs
    registra os serviços

Container de DI
    cria e conecta os objetos

Controller
    recebe e utiliza suas dependências
```

Essa organização reduz o acoplamento e mantém cada parte da aplicação concentrada em sua própria responsabilidade.
