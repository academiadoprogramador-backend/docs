## Validação de Modelos no ASP.NET MVC

Nas aulas anteriores, criamos formulários com:

- ViewModels;
- TagHelpers;
- Controllers;
- Bootstrap;
- mensagens de validação preparadas nas Views.

Agora podemos dar um passo importante.

Precisamos impedir que dados inválidos sejam utilizados pela aplicação.

Um fornecedor sem nome não deve ser cadastrado.

Um telefone em formato incorreto não deve ser aceito.

Um CNPJ com quantidade errada de dígitos não deve ser armazenado.

Para tratar essas situações, o ASP.NET Core MVC oferece recursos como:

- `DataAnnotations`;
- `ModelState`;
- TagHelpers de validação;
- classes de estilo do Bootstrap.

Esses recursos trabalham juntos, mas cada um possui uma responsabilidade diferente.

## O problema de aceitar qualquer valor

Considere uma ViewModel de cadastro:

```csharp
public record CadastrarFornecedorViewModel(
    string Nome,
    string Telefone,
    string Cnpj
);
```

Essa ViewModel define quais dados o formulário envia.

Mas ela ainda não informa quais valores são válidos.

O usuário poderia enviar:

```text
Nome: A
Telefone: abc
CNPJ: 123
```

O Controller receberia os valores normalmente.

Se não houver uma validação, a aplicação poderia tentar criar e salvar um fornecedor com dados incorretos.

Isso pode gerar problemas como:

- dados incompletos;
- formatos diferentes para a mesma informação;
- dificuldade para pesquisar registros;
- mensagens de erro apenas depois que o dado já foi salvo;
- regras repetidas em vários Controllers.

Por isso, a aplicação precisa verificar os dados antes de executar a operação.

## O que é validação?

Validação é o processo de verificar se um valor atende às regras esperadas.

Por exemplo, podemos verificar se:

- um campo foi preenchido;
- um texto possui tamanho adequado;
- um e-mail tem formato válido;
- um número está dentro de um intervalo;
- um texto segue determinado padrão.

No formulário de fornecedores, podemos definir regras como:

```text
Nome
    obrigatório e entre 2 e 100 caracteres

Telefone
    obrigatório e no formato (DDD) 90000-0000

CNPJ
    obrigatório e com formato válido
```

Essas regras devem ser conhecidas antes de cadastrar ou editar o fornecedor.

## Validação no servidor e no navegador

Uma aplicação web pode validar os dados em mais de um lugar.

### Validação no navegador

A validação no navegador acontece antes do formulário ser enviado ao servidor.

Ela pode ajudar o usuário a corrigir um erro rapidamente.

Por exemplo, o navegador pode indicar que um campo obrigatório está vazio.

### Validação no servidor

A validação no servidor acontece depois que a requisição chega ao ASP.NET.

Ela é indispensável porque o servidor não pode confiar apenas no navegador.

O usuário pode:

- desabilitar o JavaScript;
- enviar uma requisição manualmente;
- alterar o HTML do formulário;
- utilizar outra aplicação para chamar a URL.

Por isso:

> a validação no navegador melhora a experiência, mas a validação no servidor protege o processamento da aplicação.

Nesta aula, o foco será a validação no servidor usando `DataAnnotations` e `ModelState`.

Depois veremos como os TagHelpers e o Bootstrap exibem os erros para o usuário.

## O que são DataAnnotations?

`DataAnnotations` são atributos do .NET usados para descrever regras sobre propriedades e parâmetros.

Esses atributos ficam no namespace:

```csharp
System.ComponentModel.DataAnnotations
```

Por isso, normalmente adicionamos:

```csharp
using System.ComponentModel.DataAnnotations;
```

Um atributo é escrito entre colchetes:

```csharp
[Required]
string Nome
```

Nesse exemplo, `[Required]` informa que `Nome` é obrigatório.

O ASP.NET MVC utiliza essas informações quando recebe os dados do formulário.

## O atributo Required

O atributo `[Required]` indica que o campo precisa receber um valor.

Exemplo:

```csharp
public record CadastrarFornecedorViewModel(
    [Required]
    string Nome
);
```

Se o formulário for enviado sem preencher `Nome`, a validação será considerada inválida.

Também podemos definir uma mensagem personalizada:

```csharp
public record CadastrarFornecedorViewModel(
    [Required(ErrorMessage = "O campo Nome é obrigatório.")]
    string Nome
);
```

A mensagem personalizada é útil porque:

- pode ser escrita em português;
- pode explicar melhor o problema;
- aparece diretamente para o usuário;
- mantém a regra próxima do campo ao qual pertence.

## O atributo StringLength

`[StringLength]` limita o tamanho de um texto.

Podemos informar o tamanho máximo:

```csharp
[StringLength(100)]
string Nome
```

Nesse caso, o nome pode ter no máximo 100 caracteres.

Também podemos definir um tamanho mínimo:

```csharp
[StringLength(100, MinimumLength = 2)]
string Nome
```

Agora o valor precisa possuir entre 2 e 100 caracteres.

É possível personalizar a mensagem:

```csharp
[StringLength(
    100,
    MinimumLength = 2,
    ErrorMessage = "O campo Nome deve conter entre 2 e 100 caracteres."
)]
string Nome
```

O atributo não substitui o `[Required]`.

Se o campo também for obrigatório, usamos os dois atributos:

```csharp
[Required(ErrorMessage = "O campo Nome é obrigatório.")]
[StringLength(
    100,
    MinimumLength = 2,
    ErrorMessage = "O campo Nome deve conter entre 2 e 100 caracteres."
)]
string Nome
```

## O atributo RegularExpression

`[RegularExpression]` verifica se um texto corresponde a um padrão.

Esse padrão é escrito usando uma expressão regular.

Para validar um telefone como `(41) 99999-9999`, podemos utilizar:

```csharp
[RegularExpression(
    @"^\(\d{2}\) \d{4,5}-\d{4}$",
    ErrorMessage = "O campo Telefone deve estar no formato (DDD) 90000-0000."
)]
string Telefone
```

O padrão permite telefones com:

- dois dígitos para o DDD;
- quatro ou cinco dígitos antes do hífen;
- quatro dígitos depois do hífen.

Alguns valores aceitos seriam:

```text
(41) 3333-4444
(41) 99999-8888
```

Alguns valores rejeitados seriam:

```text
4133334444
(41) 333-4444
(410) 99999-8888
```

No exemplo do CNPJ da referência, usamos uma expressão que aceita o CNPJ com ou sem pontuação:

```csharp
[RegularExpression(
    @"^\d{2}\.?\d{3}\.?\d{3}\/?\d{4}-?\d{2}$",
    ErrorMessage = "O campo CNPJ deve conter 14 dígitos."
)]
string Cnpj
```

Ao escrever uma expressão regular, precisamos testar exemplos válidos e inválidos.

Uma expressão incorreta pode aceitar valores que deveriam ser rejeitados ou rejeitar valores corretos.

## Corrigindo o exemplo do CNPJ

Na expressão usada pelo projeto de referência, a barra `/` é opcional por meio do trecho `\/?`.

O padrão completo fica:

```csharp
@"^\d{2}\.?\d{3}\.?\d{3}\/?\d{4}-?\d{2}$"
```

Esse padrão permite, por exemplo:

```text
12.345.678/0001-90
12345678000190
12.345.6780001-90
```

O importante para esta aula é compreender que `[RegularExpression]` associa uma regra de formato à propriedade.

Em aplicações reais, também pode ser necessário validar se o CNPJ é matematicamente válido.

Esse tipo de regra é diferente de verificar apenas o formato dos caracteres.

## O atributo Range

`[Range]` restringe um valor numérico a um intervalo.

Exemplo:

```csharp
public record CadastrarMedicamentoViewModel(
    [Required]
    [Range(0, 100000, ErrorMessage = "A quantidade deve estar entre 0 e 100000.")]
    int QuantidadeEmEstoque
);
```

Nesse caso, valores menores que 0 ou maiores que 100000 são rejeitados.

O `Range` pode ser usado com outros tipos numéricos, como `decimal`.

## Outros atributos comuns

Além dos atributos apresentados, existem outros atributos de validação:

- `[EmailAddress]`, para verificar um formato de e-mail;
- `[Compare]`, para comparar duas propriedades;
- `[Url]`, para verificar um endereço de internet;
- `[CreditCard]`, para verificar um formato de cartão;
- `[Phone]`, para uma validação básica de telefone.

Exemplo de e-mail:

```csharp
public record CadastrarUsuarioViewModel(
    [Required(ErrorMessage = "O e-mail é obrigatório.")]
    [EmailAddress(ErrorMessage = "Informe um e-mail válido.")]
    string Email
);
```

Cada atributo representa uma regra específica.

Quando uma regra for muito particular da aplicação, podemos precisar de uma validação personalizada.

Esse assunto pode ser aprofundado depois de compreendermos o fluxo padrão com `DataAnnotations`.

## DataAnnotations na ViewModel

As regras de entrada de uma tela normalmente devem ficar na ViewModel.

Observe a ViewModel de cadastro de fornecedor da referência:

```csharp
using System.ComponentModel.DataAnnotations;

public record CadastrarFornecedorViewModel(
    [Required(ErrorMessage = "O campo Nome é obrigatório.")]
    [StringLength(
        100,
        MinimumLength = 2,
        ErrorMessage = "O campo Nome deve conter entre 2 e 100 caracteres."
    )]
    string Nome,

    [Required(ErrorMessage = "O campo Telefone é obrigatório.")]
    [RegularExpression(
        @"^\(\d{2}\) \d{4,5}-\d{4}$",
        ErrorMessage = "O campo Telefone deve estar no formato (DDD) 90000-0000."
    )]
    string Telefone,

    [Required(ErrorMessage = "O campo CNPJ é obrigatório.")]
    [RegularExpression(
        @"^\d{2}\.?\d{3}\.?\d{3}\/?\d{4}-?\d{2}$",
        ErrorMessage = "O campo CNPJ deve conter 14 dígitos."
    )]
    string Cnpj
);
```

Cada propriedade possui regras relacionadas à tela de cadastro.

Isso deixa claro o que o formulário espera receber.

## Model, ViewModel e validação

O Model e a ViewModel podem possuir responsabilidades diferentes.

O Model representa uma entidade do sistema.

A ViewModel representa os dados de uma tela.

Por isso, as regras de entrada do formulário podem ser colocadas na ViewModel:

```csharp
public record CadastrarFornecedorViewModel(
    [Required]
    [StringLength(100, MinimumLength = 2)]
    string Nome
);
```

O cadastro não precisa receber um `Id`, então a ViewModel de cadastro não possui essa propriedade.

Já a ViewModel de edição possui o identificador:

```csharp
public record EditarFornecedorViewModel(
    int Id,

    [Required]
    [StringLength(100, MinimumLength = 2)]
    string Nome
);
```

Assim, cada operação pode declarar os campos e as regras de que precisa.

## O que é ModelState?

`ModelState` é uma estrutura mantida pelo ASP.NET MVC durante o processamento da requisição.

Ela reúne informações sobre os valores recebidos e os erros de validação encontrados.

Quando o formulário é enviado, o ASP.NET:

1. lê os valores enviados pelo formulário;
2. tenta montar a ViewModel;
3. executa as validações das `DataAnnotations`;
4. registra os erros em `ModelState`;
5. entrega a ViewModel e o `ModelState` para a Action.

Podemos imaginar o resultado assim:

```text
ModelState
    Nome
        valor recebido: "A"
        erro: deve conter entre 2 e 100 caracteres

    Telefone
        valor recebido: "abc"
        erro: formato inválido
```

O Controller consulta essa estrutura para decidir se pode continuar.

## A propriedade ModelState.IsValid

`ModelState.IsValid` indica se os dados recebidos passaram pelas validações.

Se todos os campos forem válidos:

```csharp
ModelState.IsValid == true
```

Se pelo menos uma regra falhar:

```csharp
ModelState.IsValid == false
```

O padrão mais comum em uma Action `POST` é:

```csharp
[HttpPost]
public ActionResult Cadastrar(CadastrarFornecedorViewModel cadastrarVm)
{
    if (!ModelState.IsValid)
        return View(cadastrarVm);

    // cadastro do fornecedor

    return RedirectToAction(nameof(Listar));
}
```

Quando o estado é inválido, retornamos a mesma View.

Quando o estado é válido, podemos executar o cadastro e redirecionar para a listagem.

## Por que retornar a mesma ViewModel?

Quando retornamos:

```csharp
return View(cadastrarVm);
```

enviamos novamente para a View os valores que o usuário informou.

Isso permite que:

- os campos continuem preenchidos;
- o usuário veja onde ocorreu o erro;
- ele corrija apenas o que for necessário;
- os dados não sejam perdidos após o envio.

Se retornarmos a View sem enviar a ViewModel:

```csharp
return View();
```

os valores preenchidos podem não ser reapresentados corretamente.

Por isso, o padrão é devolver a ViewModel recebida quando a validação falhar.

## Action de cadastro completa

Observe uma Action completa:

```csharp
[HttpPost]
public ActionResult Cadastrar(CadastrarFornecedorViewModel cadastrarVm)
{
    Fornecedor fornecedor = new Fornecedor(
        cadastrarVm.Nome,
        cadastrarVm.Telefone,
        cadastrarVm.Cnpj
    );

    if (!ModelState.IsValid)
        return View(cadastrarVm);

    repositorio.Cadastrar(fornecedor);

    return RedirectToAction(nameof(Listar));
}
```

O fluxo é:

1. o ASP.NET recebe o formulário;
2. cria `CadastrarFornecedorViewModel`;
3. executa as `DataAnnotations`;
4. preenche `ModelState`;
5. a Action verifica `ModelState.IsValid`;
6. se houver erro, retorna a ViewModel para a View;
7. se estiver tudo correto, cadastra o fornecedor;
8. depois redireciona para a listagem.

Uma forma alternativa é verificar o `ModelState` antes de criar o Model:

```csharp
[HttpPost]
public ActionResult Cadastrar(CadastrarFornecedorViewModel cadastrarVm)
{
    if (!ModelState.IsValid)
        return View(cadastrarVm);

    Fornecedor fornecedor = new Fornecedor(
        cadastrarVm.Nome,
        cadastrarVm.Telefone,
        cadastrarVm.Cnpj
    );

    repositorio.Cadastrar(fornecedor);

    return RedirectToAction(nameof(Listar));
}
```

Essa ordem evita criar o Model quando a entrada já é inválida.

## O ModelState também recebe erros de regras de negócio

As `DataAnnotations` são úteis para regras de entrada.

Mas algumas regras dependem de dados já existentes.

Por exemplo:

> o sistema não deve permitir dois fornecedores com o mesmo CNPJ.

Essa regra não pode ser verificada apenas com `[RegularExpression]`.

O formato do CNPJ pode estar correto, mas o valor pode já existir no repositório.

Nesse caso, podemos adicionar um erro manualmente:

```csharp
[HttpPost]
public ActionResult Cadastrar(CadastrarFornecedorViewModel cadastrarVm)
{
    if (repositorio.ExisteCnpj(cadastrarVm.Cnpj))
    {
        ModelState.AddModelError(
            nameof(cadastrarVm.Cnpj),
            "Já existe um fornecedor com este CNPJ."
        );
    }

    if (!ModelState.IsValid)
        return View(cadastrarVm);

    Fornecedor fornecedor = new Fornecedor(
        cadastrarVm.Nome,
        cadastrarVm.Telefone,
        cadastrarVm.Cnpj
    );

    repositorio.Cadastrar(fornecedor);

    return RedirectToAction(nameof(Listar));
}
```

`ModelState.AddModelError` adiciona uma mensagem à chave informada.

Neste exemplo, a chave é `Cnpj`.

O TagHelper `asp-validation-for="Cnpj"` poderá exibir essa mensagem no campo correspondente.

## Erro de campo e erro geral

Um erro pode estar relacionado a uma propriedade específica:

```csharp
ModelState.AddModelError(
    nameof(cadastrarVm.Cnpj),
    "Já existe um fornecedor com este CNPJ."
);
```

Também podemos adicionar um erro geral, sem associá-lo a uma propriedade:

```csharp
ModelState.AddModelError(
    string.Empty,
    "Não foi possível concluir o cadastro."
);
```

Erros de campo aparecem junto ao campo correspondente.

Erros gerais podem aparecer no resumo de validação.

## TagHelpers de validação

Os TagHelpers conectam a View às informações do `ModelState`.

Os dois mais utilizados são:

- `asp-validation-for`;
- `asp-validation-summary`.

Eles funcionam em conjunto com os atributos `asp-for` dos campos.

## O TagHelper asp-validation-for

`asp-validation-for` exibe a mensagem de erro de uma propriedade específica.

Exemplo:

```html
<label asp-for="Nome"></label>
<input asp-for="Nome">
<span asp-validation-for="Nome"></span>
```

O `asp-for="Nome"` conecta o input à propriedade `Nome`.

O `asp-validation-for="Nome"` conecta o `span` aos erros dessa mesma propriedade.

Com Bootstrap, podemos adicionar a classe `text-danger`:

```html
<span class="text-danger" asp-validation-for="Nome"></span>
```

O Bootstrap aplica uma cor de destaque para mensagens de erro.

O TagHelper continua sendo responsável por inserir a mensagem.

O Bootstrap é responsável pela aparência.

## O TagHelper asp-validation-summary

`asp-validation-summary` exibe um resumo dos erros.

Para exibir todos os erros:

```html
<div asp-validation-summary="All" class="text-danger"></div>
```

Esse resumo pode apresentar:

- erros gerados pelas `DataAnnotations`;
- erros adicionados com `ModelState.AddModelError`;
- erros de conversão de valores;
- erros gerais sem uma propriedade específica.

Também podemos usar `ModelOnly`:

```html
<div asp-validation-summary="ModelOnly" class="text-danger"></div>
```

Nesse caso, o resumo mostra apenas erros relacionados ao Model, sem repetir necessariamente os erros individuais dos campos.

As opções mais comuns são:

```text
All
    exibe todos os erros

ModelOnly
    exibe erros gerais do Model

None
    não exibe o resumo
```

## Formulário sem mensagens de validação

Um formulário pode estar ligado à ViewModel e ainda não mostrar os erros:

```html
@model CadastrarFornecedorViewModel

<form asp-action="Cadastrar" method="post">
    <label asp-for="Nome"></label>
    <input asp-for="Nome">

    <button type="submit">Cadastrar</button>
</form>
```

O `asp-for` cria o campo corretamente.

Mas não existe nenhum elemento para exibir a mensagem quando a validação falhar.

Precisamos adicionar os TagHelpers de validação:

```html
@model CadastrarFornecedorViewModel

<form asp-action="Cadastrar" method="post">
    <div asp-validation-summary="All" class="text-danger"></div>

    <label asp-for="Nome"></label>
    <input asp-for="Nome">
    <span asp-validation-for="Nome" class="text-danger"></span>

    <button type="submit">Cadastrar</button>
</form>
```

Agora o usuário pode ver o erro geral e o erro próximo ao campo.

## Aplicando Bootstrap ao formulário

O Bootstrap não executa a validação do ModelState.

Ele fornece classes para melhorar a apresentação do formulário e das mensagens.

Um campo estilizado pode ser escrito assim:

```html
<div class="mb-3">
    <label class="form-label" asp-for="Nome"></label>
    <input class="form-control" asp-for="Nome" type="text">
    <span class="text-danger" asp-validation-for="Nome"></span>
</div>
```

Nesse exemplo:

- `mb-3` adiciona espaço abaixo do grupo;
- `form-label` estiliza o label;
- `form-control` estiliza o input;
- `text-danger` destaca a mensagem de erro;
- `asp-for` conecta o campo à ViewModel;
- `asp-validation-for` exibe o erro da propriedade.

As responsabilidades continuam separadas:

```text
DataAnnotations
    define as regras

ModelState
    armazena os valores e erros

TagHelpers
    inserem os campos e mensagens no HTML

Bootstrap
    melhora a aparência da View
```

## Formulário de cadastro de fornecedor

A View de cadastro da referência pode ser organizada assim:

```html
@model CadastrarFornecedorViewModel

@{
    Layout = "_Layout";
    ViewBag.Titulo = "Cadastro de Fornecedor";
}

<div class="row justify-content-start">
    <form class="col-lg-6" asp-action="Cadastrar" method="post">
        <div asp-validation-summary="All" class="text-danger"></div>

        <div class="mb-3">
            <label class="form-label" asp-for="Nome"></label>
            <input class="form-control" asp-for="Nome" type="text">
            <span class="text-danger" asp-validation-for="Nome"></span>
        </div>

        <div class="mb-3">
            <label class="form-label" asp-for="Telefone"></label>
            <input class="form-control" asp-for="Telefone" type="text">
            <span class="text-danger" asp-validation-for="Telefone"></span>
        </div>

        <div class="mb-3">
            <label class="form-label" asp-for="Cnpj">CNPJ</label>
            <input class="form-control" asp-for="Cnpj" type="text">
            <span class="text-danger" asp-validation-for="Cnpj"></span>
        </div>

        <div class="d-flex gap-3 mt-4">
            <button class="btn btn-primary" type="submit">
                Cadastrar
            </button>

            <a class="btn btn-outline-secondary" asp-action="Listar">
                Voltar para a lista
            </a>
        </div>
    </form>
</div>
```

O formulário utiliza os mesmos nomes das propriedades da ViewModel.

Por isso, o ASP.NET consegue associar:

```text
Nome
    input, label e mensagem de Nome

Telefone
    input, label e mensagem de Telefone

Cnpj
    input, label e mensagem de Cnpj
```

## O que acontece quando o Nome está inválido?

Considere que o usuário envie:

```text
Nome: A
Telefone: (41) 99999-8888
CNPJ: 12.345.678/0001-90
```

O ASP.NET executará a regra:

```csharp
[StringLength(100, MinimumLength = 2)]
string Nome
```

Como `A` possui apenas um caractere, a regra falha.

O erro é adicionado ao `ModelState` com a chave `Nome`.

Depois, a Action verifica:

```csharp
if (!ModelState.IsValid)
    return View(cadastrarVm);
```

A View é renderizada novamente.

O TagHelper encontra o erro para `Nome`:

```html
<span class="text-danger" asp-validation-for="Nome"></span>
```

E renderiza a mensagem correspondente.

O valor `A` continua no input para que o usuário possa corrigi-lo.

## O que acontece quando o telefone está inválido?

Considere o valor:

```text
Telefone: 41999998888
```

Ele não corresponde ao padrão definido:

```csharp
@"^\(\d{2}\) \d{4,5}-\d{4}$"
```

O `ModelState` recebe um erro para `Telefone`.

O TagHelper do campo exibe essa mensagem:

```html
<span class="text-danger" asp-validation-for="Telefone"></span>
```

O Bootstrap aplica a classe visual `text-danger`.

Assim, a mensagem fica destacada sem que o Controller precise montar HTML manualmente.

## O que acontece quando vários campos estão inválidos?

Imagine que o formulário seja enviado vazio.

Nesse caso, várias regras podem falhar ao mesmo tempo:

- `Nome` é obrigatório;
- `Telefone` é obrigatório;
- `Cnpj` é obrigatório.

Cada erro fica associado à sua propriedade.

Os `span` individuais exibem as mensagens próximas aos campos:

```html
<span class="text-danger" asp-validation-for="Nome"></span>
<span class="text-danger" asp-validation-for="Telefone"></span>
<span class="text-danger" asp-validation-for="Cnpj"></span>
```

O resumo também pode apresentar os erros:

```html
<div asp-validation-summary="All" class="text-danger"></div>
```

Podemos utilizar os dois recursos ao mesmo tempo.

O resumo oferece uma visão geral.

As mensagens individuais mostram exatamente qual campo precisa ser corrigido.

## Validação da View de edição

A View de edição também precisa exibir mensagens de validação.

Um formulário de edição pode ser escrito assim:

```html
@model EditarFornecedorViewModel

<form asp-action="Editar" asp-route-id="@Model.Id" method="post">
    <div asp-validation-summary="All" class="text-danger"></div>

    <div class="mb-3">
        <label class="form-label" asp-for="Nome"></label>
        <input class="form-control" asp-for="Nome" type="text">
        <span class="text-danger" asp-validation-for="Nome"></span>
    </div>

    <div class="mb-3">
        <label class="form-label" asp-for="Telefone"></label>
        <input class="form-control" asp-for="Telefone" type="text">
        <span class="text-danger" asp-validation-for="Telefone"></span>
    </div>

    <div class="mb-3">
        <label class="form-label" asp-for="Cnpj">CNPJ</label>
        <input class="form-control" asp-for="Cnpj" type="text">
        <span class="text-danger" asp-validation-for="Cnpj"></span>
    </div>

    <button class="btn btn-primary" type="submit">
        Confirmar edição
    </button>
</form>
```

As mesmas regras da ViewModel são utilizadas no cadastro e na edição.

Isso evita que cada Action implemente as regras manualmente.

## Mensagens personalizadas

As mensagens padrão dos atributos podem não estar adequadas ao texto da aplicação.

Por exemplo:

```csharp
[Required]
string Nome
```

pode produzir uma mensagem padrão em inglês, dependendo da configuração da aplicação.

Podemos definir a mensagem diretamente no atributo:

```csharp
[Required(ErrorMessage = "O campo Nome é obrigatório.")]
string Nome
```

Também podemos utilizar o nome exibido pelo atributo `Display`:

```csharp
[Display(Name = "Nome do fornecedor")]
[Required(ErrorMessage = "O campo {0} é obrigatório.")]
string Nome
```

O marcador `{0}` pode ser substituído pelo nome definido em `Display`.

O resultado pode ser uma mensagem como:

```text
O campo Nome do fornecedor é obrigatório.
```

Essa forma ajuda a reutilizar mensagens sem escrever o nome da propriedade diretamente.

## O atributo Display

`[Display]` define o nome apresentado para uma propriedade.

Exemplo:

```csharp
[Display(Name = "CNPJ")]
string Cnpj
```

O TagHelper do label pode utilizar esse nome:

```html
<label asp-for="Cnpj"></label>
```

O HTML gerado apresentará `CNPJ` como texto do label.

Também podemos escrever o texto manualmente:

```html
<label asp-for="Cnpj">CNPJ</label>
```

No projeto de referência, a View utiliza essa segunda forma.

## Erros de conversão

O `ModelState` também pode registrar erros que não vêm diretamente de uma `DataAnnotation`.

Um exemplo acontece quando a ViewModel espera um número:

```csharp
public record CadastrarMedicamentoViewModel(
    int QuantidadeEmEstoque
);
```

Se o usuário enviar:

```text
QuantidadeEmEstoque: abc
```

o ASP.NET não conseguirá converter o texto para `int`.

Essa falha também será registrada no `ModelState`.

O `asp-validation-for` poderá exibir a mensagem correspondente:

```html
<span class="text-danger" asp-validation-for="QuantidadeEmEstoque"></span>
```

Por isso, consultar apenas os atributos de validação não é suficiente.

O Controller deve verificar sempre:

```csharp
ModelState.IsValid
```

## Recarregando dados auxiliares após uma falha

Algumas ViewModels precisam de dados auxiliares para preencher a View.

Um formulário de medicamento pode possuir uma lista de fornecedores:

```csharp
public record CadastrarMedicamentoViewModel(
    string Nome,
    string Descricao,
    int FornecedorId
)
{
    public List<FornecedorMedicamentoViewModel> Fornecedores { get; set; } = [];
}
```

Quando a validação falha, retornamos a mesma ViewModel:

```csharp
if (!ModelState.IsValid)
    return View(viewModel);
```

Mas a lista de fornecedores também precisa estar preenchida para que o `<select>` seja renderizado corretamente.

Nesse caso, precisamos recarregar os dados auxiliares antes de retornar a View:

```csharp
if (!ModelState.IsValid)
{
    viewModel.Fornecedores = ObterFornecedores();

    return View(viewModel);
}
```

O mesmo cuidado vale para qualquer formulário que dependa de:

- listas de seleção;
- opções carregadas do banco ou repositório;
- dados exibidos em componentes auxiliares.

## Validação e redirecionamento

Quando o cadastro é concluído com sucesso, usamos um redirecionamento:

```csharp
return RedirectToAction(nameof(Listar));
```

Quando a validação falha, retornamos a View diretamente:

```csharp
return View(cadastrarVm);
```

Essa diferença é importante.

O redirecionamento inicia uma nova requisição.

Se redirecionarmos quando existem erros, o `ModelState` e os valores do formulário não serão reapresentados da mesma maneira.

Podemos resumir:

```text
Dados válidos
    salva e redireciona

Dados inválidos
    retorna a mesma View com a ViewModel
```

## O Bootstrap não valida a regra de negócio

O Bootstrap possui classes visuais.

Ele não sabe se um CNPJ já existe no repositório.

Ele não sabe se o nome de um fornecedor possui o tamanho correto.

Ele também não decide se um medicamento pode ser cadastrado.

Essas responsabilidades pertencem à aplicação:

```text
DataAnnotations
    regras de formato e entrada

ModelState
    resultado das validações

Controller
    decide se continua ou retorna a View

Repositório e domínio
    regras que dependem dos dados do sistema

Bootstrap
    aparência dos campos e mensagens
```

## Classes Bootstrap usadas nas mensagens

Algumas classes úteis no formulário são:

- `text-danger`, para destacar mensagens de erro;
- `form-control`, para estilizar inputs;
- `form-label`, para estilizar labels;
- `mb-3`, para separar os grupos de campos;
- `alert`, para criar uma área visual de destaque;
- `alert-danger`, para uma mensagem geral de erro.

Podemos exibir um resumo dentro de um alerta:

```html
<div class="alert alert-danger" role="alert">
    <div asp-validation-summary="All"></div>
</div>
```

O TagHelper insere as mensagens.

As classes `alert` e `alert-danger` controlam a aparência do contêiner.

Também podemos manter a mensagem simples:

```html
<div asp-validation-summary="All" class="text-danger"></div>
```

A escolha depende da organização visual da View.

## Validação do lado do cliente

Os TagHelpers podem gerar atributos HTML relacionados à validação.

Por exemplo, um input ligado a `[Required]` pode receber informações como:

```html
<input
    data-val="true"
    data-val-required="O campo Nome é obrigatório."
    id="Nome"
    name="Nome"
    type="text"
>
```

Esses atributos podem ser utilizados por bibliotecas de validação JavaScript.

Quando a aplicação possui os scripts necessários, o navegador pode exibir mensagens antes de enviar o formulário.

Mesmo assim, a Action deve continuar verificando o `ModelState`:

```csharp
if (!ModelState.IsValid)
    return View(viewModel);
```

A validação no servidor continua sendo obrigatória.

No projeto de referência, o fluxo principal desta aula utiliza o `ModelState` no Controller e os TagHelpers para renderizar as mensagens na View.

## Ordem recomendada para um formulário

Ao criar um formulário com validação, podemos seguir estas etapas:

1. Criar uma ViewModel para a operação.
2. Adicionar as `DataAnnotations` necessárias.
3. Criar a Action `POST` recebendo a ViewModel.
4. Verificar `ModelState.IsValid`.
5. Retornar a ViewModel quando houver erro.
6. Executar a regra de negócio quando os dados forem válidos.
7. Adicionar `asp-validation-summary` para o resumo.
8. Adicionar `asp-validation-for` em cada campo.
9. Aplicar classes do Bootstrap aos campos e mensagens.
10. Recarregar listas auxiliares quando a View for retornada após um erro.

## Checklist de uma View validada

Antes de considerar o formulário pronto, verifique se:

- a View declara a ViewModel correta;
- cada campo utiliza `asp-for`;
- cada campo possui `asp-validation-for`;
- existe um resumo quando ele for útil;
- as mensagens possuem uma classe visual adequada;
- o formulário utiliza `method="post"`;
- a Action verifica `ModelState.IsValid`;
- a Action retorna a ViewModel quando houver erro;
- listas auxiliares são preenchidas novamente quando necessário;
- o cadastro só acontece depois da validação.

## Fluxo completo da validação

O fluxo pode ser representado assim:

```text
Usuário preenche o formulário
    |
    v
TagHelpers enviam os valores
    |
    v
ASP.NET cria a ViewModel
    |
    v
DataAnnotations executam as regras
    |
    v
ModelState recebe valores e erros
    |
    v
Controller verifica ModelState.IsValid
    |
    +--> inválido: retorna a ViewModel para a View
    |              |
    |              +--> TagHelpers exibem mensagens
    |              +--> Bootstrap aplica os estilos
    |
    +--> válido: executa o cadastro e redireciona
```

Cada parte possui uma função específica.

Isso evita colocar toda a validação manualmente dentro da View ou do Controller.

## Conclusão

As `DataAnnotations` permitem declarar regras de validação próximas às propriedades da ViewModel.

A aplicação pode utilizar atributos como:

- `[Required]`;
- `[StringLength]`;
- `[RegularExpression]`;
- `[Range]`;
- `[EmailAddress]`.

O ASP.NET executa essas regras quando recebe o formulário.

Os resultados ficam disponíveis no `ModelState`.

O Controller verifica `ModelState.IsValid` para decidir se deve:

- retornar a View com mensagens de erro;
- ou continuar o processamento e redirecionar após o cadastro.

Os TagHelpers exibem os erros:

```html
<div asp-validation-summary="All"></div>
<span asp-validation-for="Nome"></span>
```

O Bootstrap melhora a apresentação:

```html
<input class="form-control" asp-for="Nome">
<span class="text-danger" asp-validation-for="Nome"></span>
```

Podemos resumir:

```text
DataAnnotations
    definem as regras

ModelState
    registra o resultado

Controller
    decide o fluxo

TagHelpers
    exibem os erros

Bootstrap
    organiza e estiliza a apresentação
```

Esse fluxo cria formulários mais seguros, claros e fáceis de manter.
