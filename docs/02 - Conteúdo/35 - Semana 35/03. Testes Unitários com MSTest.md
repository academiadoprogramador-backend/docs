## Testes Unitários com MSTest no e-Agenda

Até agora, verificamos muitas funcionalidades executando o e-Agenda e utilizando suas telas.

No módulo de Tarefas, por exemplo, podemos adicionar itens, concluí-los e observar a barra de progresso.

Porém, repetir essa conferência manual após cada alteração exige tempo.

Também é fácil esquecer um cenário, como remover o último item de uma tarefa concluída.

> Como verificar essas regras sem abrir o navegador ou preparar o banco de dados?

Nesta aula, vamos escrever testes automatizados para a entidade `Tarefa`.

Começaremos pelos cenários de criação, adição, remoção e conclusão de itens. Depois, ampliaremos a verificação para outros comportamentos.

## O que é um teste unitário?

Um teste unitário é um código que verifica um comportamento pequeno e isolado da aplicação.

No nosso exemplo, o teste cria uma `Tarefa`, executa uma operação e compara o resultado com o esperado.

Não é necessário chamar o Controller, o serviço ou o Repository.

Os objetos existem apenas na memória durante a execução do teste.

Isso permite verificar as regras do Domínio sem depender de:

- servidor web;
- usuário autenticado;
- conexão com SQL Server;
- dados cadastrados anteriormente.

Testar a gravação pelo Repository junto ao banco seria um **teste de integração**.

Testar o fluxo completo pela interface seria um **teste de ponta a ponta**.

Esses testes têm outras responsabilidades. Aqui, o foco está no comportamento das entidades.

## Quais regras de Tarefa vamos verificar?

A entidade `Tarefa` possui título, prioridade, itens e informações sobre sua conclusão.

Seu construtor recebe o título e a prioridade:

```csharp
public Tarefa(string titulo, PrioridadeTarefa prioridade) : this()
{
    Titulo = titulo;
    Prioridade = prioridade;
    RecalcularConclusao();
}
```

As operações `AdicionarItem`, `RemoverItem` e `AlterarConclusaoItem` também recalculam o progresso.

No método privado `RecalcularConclusao`, uma tarefa sem itens recebe:

```csharp
if (Itens.Count == 0)
{
    PercentualConcluido = 0;
    Concluida = false;
    DataConclusao = null;

    return;
}
```

Quando existem itens, o cálculo considera a proporção de itens concluídos:

```csharp
int itensConcluidos = Itens.Count(i => i.Concluido);

PercentualConcluido = (int)Math.Round(
    (decimal)itensConcluidos / Itens.Count * 100
);

Concluida = PercentualConcluido == 100;

DataConclusao = Concluida
    ? DataConclusao ?? DateOnly.FromDateTime(DateTime.Today)
    : null;
```

Por exemplo:

- nenhum item: 0%, pendente e sem data de conclusão;
- um de dois itens concluídos: 50%, pendente e sem data de conclusão;
- todos os itens concluídos: 100%, concluída e com data de conclusão.

> Não precisamos chamar um método privado para testá-lo. Verificamos seus efeitos pelas operações públicas da entidade.

## Preparando o projeto de testes

O projeto de testes fica separado dos projetos da aplicação:

```text
eAgenda.slnx
src/
  Dominio/
    eAgenda.Dominio.csproj
tests/
  Unidade/
    eAgenda.Testes.Unidade.csproj
    MSTestSettings.cs
    Tarefas/
      TarefaTests.cs
```

Utilizaremos o SDK do .NET 10 e o pacote `MSTest` na versão `4.0.1`.

O MSTest fornece os atributos e as asserções usados nos testes. Seu pacote também reúne as dependências necessárias para executar os testes com `dotnet test`.

Se `tests/Unidade` já existe, não crie outro projeto. Confira sua configuração e acompanhe os exemplos no arquivo `Tarefas/TarefaTests.cs`.

Para preparar essa estrutura em uma solução que ainda não possui o projeto de testes:

1. Abra o terminal na pasta que contém `eAgenda.slnx`.
2. Crie um projeto de biblioteca para os testes:

   ```bash
   dotnet new classlib -n eAgenda.Testes.Unidade -o tests/Unidade -f net10.0
   ```

3. Adicione o pacote MSTest:

   ```bash
   dotnet add tests/Unidade/eAgenda.Testes.Unidade.csproj package MSTest --version 4.0.1
   ```

4. Adicione a referência ao Domínio:

   ```bash
   dotnet add tests/Unidade/eAgenda.Testes.Unidade.csproj reference src/Dominio/eAgenda.Dominio.csproj
   ```

5. Inclua o projeto na solução:

   ```bash
   dotnet sln eAgenda.slnx add tests/Unidade/eAgenda.Testes.Unidade.csproj
   ```

O arquivo `Class1.cs`, criado pelo template de biblioteca, não será usado nesta aula e pode ser removido.

A configuração do projeto de testes fica assim:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="MSTest" Version="4.0.1" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="../../src/Dominio/eAgenda.Dominio.csproj" />
  </ItemGroup>

  <ItemGroup>
    <Using Include="Microsoft.VisualStudio.TestTools.UnitTesting" />
  </ItemGroup>
</Project>
```

A referência ao Domínio permite criar `Tarefa` e `ItemTarefa` nos testes.

O elemento `Using` disponibiliza o namespace do MSTest em todos os arquivos do projeto.

Não precisamos referenciar a Apresentação ou a Infraestrutura para testar essas regras.

## Organizando um teste com o padrão AAA

O padrão **AAA** separa o teste em três partes:

1. **Arranjo (Arrange):** preparar objetos e dados.
2. **Ação (Act):** executar o comportamento que queremos verificar.
3. **Asserção (Assert):** conferir o resultado esperado.

Uma asserção é uma verificação feita pelo teste.

Por exemplo, `Assert.AreEqual(0, tarefa.PercentualConcluido)` verifica se o percentual é igual a zero.

Se o valor for diferente, o MSTest marca o teste como falho.

O primeiro argumento de `AreEqual` é o valor esperado. O segundo é o valor obtido.

## Escrevendo o primeiro teste

Crie ou atualize `tests/Unidade/Tarefas/TarefaTests.cs`:

```csharp
using eAgenda.Dominio.Modulos.Tarefas;
using Microsoft.VisualStudio.TestTools.UnitTesting;

namespace eAgenda.Testes.Unidade.Tarefas;

[TestClass]
public sealed class TarefaTests
{
    [TestMethod]
    public void Construtor_ComDadosValidos_DeveInicializarTarefaPendente()
    {
        // Arranjo
        string titulo = "Estudar";
        PrioridadeTarefa prioridade = PrioridadeTarefa.Alta;

        // Ação
        Tarefa tarefa = new(titulo, prioridade);

        // Asserção
        Assert.AreEqual(titulo, tarefa.Titulo);
        Assert.AreEqual(prioridade, tarefa.Prioridade);
        Assert.HasCount(0, tarefa.Itens);
        Assert.AreEqual(0, tarefa.PercentualConcluido);
        Assert.IsFalse(tarefa.Concluida);
        Assert.IsNull(tarefa.DataConclusao);
    }
}
```

`[TestClass]` identifica uma classe de testes.

`[TestMethod]` identifica um método que o MSTest deve executar como teste.

O nome do método descreve o comportamento, a condição e o resultado esperado.

Mesmo com várias asserções, estamos verificando um único cenário: o estado inicial de uma tarefa.

`Assert.HasCount` verifica a quantidade de elementos da coleção.

`Assert.IsFalse` verifica se um valor é falso, enquanto `Assert.IsNull` verifica a ausência de valor.

O construtor não chama `Validar()`. Criar a entidade e validar seus dados são operações diferentes.

## Executando e interpretando os resultados

Na raiz da solução, execute:

```bash
dotnet test tests/Unidade/eAgenda.Testes.Unidade.csproj
```

O comando restaura as dependências necessárias, compila os projetos e executa os testes encontrados.

Com apenas o primeiro método, deve existir um teste aprovado.

Conforme adicionarmos métodos, a quantidade aumentará.

Para observar uma falha:

1. Troque temporariamente o percentual esperado de `0` para `100`.
2. Execute o comando novamente.
3. Leia a diferença entre o valor esperado e o obtido.
4. Restaure o valor esperado para `0` e execute novamente.

O teste deve falhar porque uma tarefa recém-criada não está concluída.

> Um teste precisa verificar o resultado correto da regra. Não altere a expectativa apenas para fazer um teste passar.

Se nenhum teste for encontrado, confira o pacote MSTest, os atributos e o caminho do projeto informado no comando.

## Testando a adição de um item concluído

Os próximos métodos devem ser adicionados **dentro da mesma classe `TarefaTests`**, após o primeiro teste.

Não substitua os testes anteriores.

Vamos preparar um item já concluído e adicioná-lo à tarefa:

```csharp
[TestMethod]
public void AdicionarItem_ComItemConcluido_DeveConcluirTarefa()
{
    // Arranjo
    Tarefa tarefa = new("Estudar", PrioridadeTarefa.Alta);
    ItemTarefa item = new(tarefa, "Organizar material de estudo");
    item.Concluir();
    DateOnly dataAntes = DateOnly.FromDateTime(DateTime.Today);

    // Ação
    tarefa.AdicionarItem(item);

    // Asserção
    DateOnly dataDepois = DateOnly.FromDateTime(DateTime.Today);

    Assert.HasCount(1, tarefa.Itens);
    Assert.AreSame(item, tarefa.Itens[0]);
    Assert.AreEqual(100, tarefa.PercentualConcluido);
    Assert.IsTrue(tarefa.Concluida);
    Assert.IsNotNull(tarefa.DataConclusao);
    Assert.IsTrue(
        tarefa.DataConclusao == dataAntes ||
        tarefa.DataConclusao == dataDepois
    );
}
```

`ItemTarefa` recebe a tarefa e o título no construtor. O método `Concluir()` altera seu estado para concluído.

Essa preparação pertence ao arranjo. A ação que estamos testando é `AdicionarItem`.

`Assert.AreSame` verifica se a coleção contém a mesma instância que foi adicionada.

Como o único item está concluído, a tarefa deve atingir 100% e receber a data atual.

Capturamos a data antes e depois da ação para evitar uma falha caso o teste atravesse a meia-noite.

O Domínio consulta o relógio do sistema. Em uma evolução futura, poderíamos fornecer uma fonte de tempo controlável para tornar essa verificação ainda mais previsível.

## Testando a conclusão de um item pendente

Agora, adicionamos um item ainda pendente e solicitamos sua conclusão pela tarefa:

```csharp
[TestMethod]
public void AlterarConclusaoItem_ComItemPendente_DeveConcluirTarefa()
{
    // Arranjo
    Tarefa tarefa = new("Estudar", PrioridadeTarefa.Alta);
    ItemTarefa item = new(tarefa, "Ler o conteúdo da aula");
    tarefa.AdicionarItem(item);

    // Ação
    bool alterou = tarefa.AlterarConclusaoItem(item.Id, true);

    // Asserção
    Assert.IsTrue(alterou);
    Assert.IsTrue(item.Concluido);
    Assert.HasCount(1, tarefa.Itens);
    Assert.AreEqual(100, tarefa.PercentualConcluido);
    Assert.IsTrue(tarefa.Concluida);
    Assert.IsNotNull(tarefa.DataConclusao);
}
```

O retorno `true` indica que o item foi encontrado.

Além desse retorno, verificamos seus efeitos: o item foi concluído e o progresso da tarefa foi atualizado.

> Chamar apenas `item.Concluir()` não recalcula o progresso da tarefa. Para isso, utilizamos a operação `AlterarConclusaoItem`.

## Testando a remoção do último item

Uma tarefa sem itens deve permanecer pendente, mesmo que estivesse concluída antes da remoção:

```csharp
[TestMethod]
public void RemoverItem_ComUnicoItemConcluido_DeveRetornarTarefaPendente()
{
    // Arranjo
    Tarefa tarefa = new("Estudar", PrioridadeTarefa.Alta);
    ItemTarefa item = new(tarefa, "Revisar anotações");
    item.Concluir();
    tarefa.AdicionarItem(item);

    // Ação
    bool removeu = tarefa.RemoverItem(item.Id);

    // Asserção
    Assert.IsTrue(removeu);
    Assert.HasCount(0, tarefa.Itens);
    Assert.AreEqual(0, tarefa.PercentualConcluido);
    Assert.IsFalse(tarefa.Concluida);
    Assert.IsNull(tarefa.DataConclusao);
}
```

Não basta verificar se a coleção ficou vazia.

Também precisamos garantir que o percentual, o estado e a data de conclusão foram recalculados.

Até aqui, cobrimos os quatro cenários iniciais do projeto, ampliando as verificações do estado inicial e dos retornos das operações.

## Ampliando os cenários: progresso parcial

Testar apenas 0% e 100% pode deixar um erro no cálculo intermediário passar despercebido.

Vamos concluir um de dois itens:

```csharp
[TestMethod]
public void AlterarConclusaoItem_ComUmDeDoisItensConcluidos_DeveCalcularCinquentaPorCento()
{
    // Arranjo
    Tarefa tarefa = new("Estudar", PrioridadeTarefa.Alta);
    ItemTarefa primeiroItem = new(tarefa, "Ler a aula");
    ItemTarefa segundoItem = new(tarefa, "Resolver os exercícios");
    tarefa.AdicionarItem(primeiroItem);
    tarefa.AdicionarItem(segundoItem);

    // Ação
    bool alterou = tarefa.AlterarConclusaoItem(primeiroItem.Id, true);

    // Asserção
    Assert.IsTrue(alterou);
    Assert.IsTrue(primeiroItem.Concluido);
    Assert.IsFalse(segundoItem.Concluido);
    Assert.AreEqual(50, tarefa.PercentualConcluido);
    Assert.IsFalse(tarefa.Concluida);
    Assert.IsNull(tarefa.DataConclusao);
}
```

Esse teste verifica um resultado diferente dos extremos.

Também confirma que concluir um item não conclui os demais.

## Testando a reabertura de um item

Uma tarefa concluída pode voltar a ficar pendente.

Esse caminho precisa de seu próprio teste:

```csharp
[TestMethod]
public void AlterarConclusaoItem_AoReabrirUnicoItem_DeveLimparConclusaoDaTarefa()
{
    // Arranjo
    Tarefa tarefa = new("Estudar", PrioridadeTarefa.Alta);
    ItemTarefa item = new(tarefa, "Resolver os exercícios");
    item.Concluir();
    tarefa.AdicionarItem(item);

    // Ação
    bool alterou = tarefa.AlterarConclusaoItem(item.Id, false);

    // Asserção
    Assert.IsTrue(alterou);
    Assert.IsFalse(item.Concluido);
    Assert.AreEqual(0, tarefa.PercentualConcluido);
    Assert.IsFalse(tarefa.Concluida);
    Assert.IsNull(tarefa.DataConclusao);
}
```

O parâmetro `false` solicita a remoção da conclusão.

Observe que não estamos apenas mudando um booleano: também verificamos se a data anterior foi removida.

## Testando um identificador inexistente

`RemoverItem` retorna `false` quando não encontra o identificador informado.

Nesse caso, não deve remover outro item ou alterar o progresso:

```csharp
[TestMethod]
public void RemoverItem_ComIdInexistente_DeveManterEstadoDaTarefa()
{
    // Arranjo
    Tarefa tarefa = new("Estudar", PrioridadeTarefa.Alta);
    ItemTarefa item = new(tarefa, "Revisar anotações");
    item.Concluir();
    tarefa.AdicionarItem(item);
    DateOnly? dataConclusaoAnterior = tarefa.DataConclusao;

    // Ação
    bool removeu = tarefa.RemoverItem(Guid.Empty);

    // Asserção
    Assert.IsFalse(removeu);
    Assert.HasCount(1, tarefa.Itens);
    Assert.AreSame(item, tarefa.Itens[0]);
    Assert.AreEqual(100, tarefa.PercentualConcluido);
    Assert.IsTrue(tarefa.Concluida);
    Assert.AreEqual(dataConclusaoAnterior, tarefa.DataConclusao);
}
```

As entidades recebem um `Id` ao serem criadas. Por isso, `Guid.Empty` representa um identificador ausente nesse arranjo.

Não precisamos esperar uma exceção: o contrato dessa operação comunica a ausência pelo retorno booleano.

## Reutilizando um teste com DataRow

O método `Validar()` verifica, entre outras regras, se o título possui de 2 a 100 caracteres.

Podemos executar o mesmo teste para diferentes títulos com `[DataRow]`:

```csharp
[TestMethod]
[DataRow("")]
[DataRow(" ")]
[DataRow("A")]
public void Validar_ComTituloInvalido_DeveRetornarErroNoTitulo(string titulo)
{
    // Arranjo
    Tarefa tarefa = new(titulo, PrioridadeTarefa.Normal);

    // Ação
    var erros = tarefa.Validar();

    // Asserção
    Assert.HasCount(1, erros);
    Assert.AreEqual(nameof(Tarefa.Titulo), erros[0].Campo);
    Assert.AreEqual(
        "O campo \"Título\" deve conter entre 2 e 100 caracteres.",
        erros[0].Mensagem
    );
}
```

Cada `DataRow` fornece um valor para o parâmetro `titulo`.

O MSTest executa o método uma vez para cada linha de dados.

Assim, verificamos título vazio, título em branco e título curto sem repetir todo o código.

A prioridade utilizada é válida para que o teste isole o problema no título.

Observe que `Validar()` retorna uma lista de `ErroValidacao`, com `Campo` e `Mensagem`. Ele não lança uma exceção para esses dados.

## Mantendo os testes independentes

Cada teste desta aula cria seus próprios objetos.

Nenhum deles depende de outro método ser executado antes.

O projeto também pode utilizar `MSTestSettings.cs` para permitir execução paralela:

```csharp
using Microsoft.VisualStudio.TestTools.UnitTesting;

[assembly: Parallelize(Scope = ExecutionScope.MethodLevel)]
```

Isso permite ao executor executar métodos de teste em paralelo.

Compartilhar uma mesma `Tarefa` em um campo `static` faria os testes disputarem e alterarem o mesmo estado.

Prefira arranjos locais e independentes.

Também evite depender de:

- ordem de execução dos testes;
- identificadores fixos gerados em outro teste;
- dados reais do banco;
- pausas artificiais para aguardar alterações.

Se houver preparação repetida, o MSTest oferece `[TestInitialize]`, executado antes de cada teste. Por enquanto, manter o arranjo no próprio método facilita a leitura.

## Exercícios para ampliar a cobertura

Adicione novos testes para verificar:

1. A conclusão de um item com identificador inexistente, esperando `false` e estado inalterado.
2. A remoção do item pendente quando outro item já está concluído, esperando 100%.
3. Um de três itens concluídos, esperando 33% pelo arredondamento utilizado.
4. Um título com 101 caracteres, esperando erro de validação.
5. Títulos com exatamente 2 e 100 caracteres, esperando ausência de erros com prioridade válida.
6. Uma prioridade que não pertence ao enum, esperando erro no campo `Prioridade`.

Para gerar um título longo, utilize `new string('A', 101)`.

Para representar uma prioridade inválida, utilize `(PrioridadeTarefa)99`.

Execute os testes após cada cenário adicionado.

## O que esses testes garantem?

Os testes verificam comportamentos observáveis da entidade `Tarefa`.

Eles ajudam a detectar regressões: erros introduzidos em comportamentos que antes funcionavam.

Porém, não comprovam que o Repository grava corretamente, que o QueryFilter isola os usuários ou que a tela mostra o progresso.

Essas verificações exigem outros tipos de teste.

> Ter testes aprovados significa que os cenários verificados passaram, não que todos os possíveis problemas da aplicação foram eliminados.

Com MSTest e o padrão AAA, conseguimos transformar regras do Domínio em verificações rápidas, repetíveis e fáceis de entender.
