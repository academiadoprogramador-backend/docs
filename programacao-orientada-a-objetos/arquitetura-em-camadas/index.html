Arquitetura em Camadas

O problema de deixar tudo no mesmo lugar​

No começo, é comum escrever quase todo o programa dentro do Program.cs.

Isso funciona enquanto o sistema é pequeno.

Por exemplo, em uma aplicação de console, podemos ter no mesmo arquivo:

  • o menu principal;
  • a leitura dos dados digitados pelo usuário;
  • a criação dos objetos;
  • as regras do sistema;
  • o armazenamento dos registros em arrays.

O problema aparece quando o projeto cresce.

Imagine um sistema de gestão de equipamentos.

Ele começa controlando apenas equipamentos.

Depois passa a controlar chamados.

Depois precisa editar, excluir, listar, buscar equipamentos e associar chamados a equipamentos.

Se tudo estiver misturado, qualquer alteração fica mais difícil.

Ao mexer no menu, podemos quebrar o armazenamento.

Ao mexer no cadastro, podemos alterar sem querer a listagem.

Ao adicionar chamados, o Program.cs começa a ficar grande demais.

Quanto mais responsabilidades uma classe acumula, mais difícil fica entender, testar e alterar essa classe.

O que são camadas?​

Camadas são divisões do sistema por responsabilidade.

Cada camada agrupa classes que têm um papel parecido dentro da aplicação.

Em vez de pensar apenas em arquivos soltos, começamos a pensar em perguntas:

  • quem conversa com o usuário?
  • quem representa os dados importantes do sistema?
  • quem guarda e recupera esses dados?
  • quem coordena o fluxo da aplicação?

Quando respondemos essas perguntas, o código começa a ganhar organização.

Essa organização não muda o objetivo do sistema.

O sistema ainda cadastra equipamentos e chamados.

O que muda é onde cada responsabilidade fica.

O modelo de 3 camadas​

Um modelo bastante usado no início é a arquitetura em 3 camadas.

Neste modelo, separamos a aplicação em:

  • camada de apresentação;
  • camada de domínio;
  • camada de infraestrutura.

Esses nomes podem mudar em outros projetos.

Mas a ideia principal continua a mesma:

cada parte do sistema deve ter uma responsabilidade clara.

No repositório academiadoprogramador-backend/gestao-de-equipamentos-2026, a branch v3 mostra essa separação dentro do projeto GestaoDeEquipamentos.ConsoleApp.

A estrutura fica parecida com esta:

GestaoDeEquipamentos.ConsoleApp/
├── Apresentacao/
│   ├── TelaChamado.cs
│   ├── TelaEquipamento.cs
│   └── TelaPrincipal.cs
├── Dominio/
│   ├── Chamado.cs
│   └── Equipamento.cs
├── Infraestrutura/
│   ├── RepositorioChamado.cs
│   └── RepositorioEquipamento.cs
└── Program.cs

Vamos entender cada uma dessas partes.

Camada de apresentação​

A camada de apresentação é a parte do sistema que conversa com o usuário.

Em uma aplicação de console, isso significa usar comandos como:

  • Console.WriteLine;
  • Console.Write;
  • Console.ReadLine;
  • Console.Clear.

No projeto de gestão de equipamentos, essa camada aparece na pasta Apresentacao.

Ela contém classes como:

  • TelaPrincipal;
  • TelaEquipamento;
  • TelaChamado.

A TelaPrincipal mostra o menu principal da aplicação.

A TelaEquipamento mostra as opções de cadastro, edição, exclusão e visualização de equipamentos.

A TelaChamado faz o mesmo para chamados.

Um exemplo simplificado seria:

public class TelaPrincipal
{
    public string? ObterOpcaoMenuPrincipal()
    {
        Console.WriteLine("1 - Controle de equipamentos");
        Console.WriteLine("2 - Controle de chamados");
        Console.WriteLine("S - Sair");

        return Console.ReadLine()?.ToUpper();
    }
}

Repare que essa classe não representa um equipamento.

Ela também não guarda os equipamentos.

A responsabilidade dela é apresentar opções e ler a escolha do usuário.

Camada de domínio​

A camada de domínio representa os conceitos principais do sistema.

No projeto, ela fica na pasta Dominio.

Ela contém classes como:

  • Equipamento;
  • Chamado.

Essas classes representam aquilo que existe no problema que estamos resolvendo.

Um equipamento tem dados como:

  • identificador;
  • nome;
  • preço de aquisição;
  • data de fabricação.

Um chamado tem dados como:

  • identificador;
  • título;
  • descrição;
  • data de abertura;
  • equipamento relacionado.

No projeto, a classe Chamado possui uma referência para Equipamento.

Isso mostra uma relação importante do domínio:

um chamado é aberto para um equipamento.

Um exemplo simplificado seria:

public class Chamado
{
    public int id;
    public string titulo;
    public string descricao;
    public DateTime dataAbertura;
    public Equipamento equipamento;
}

A camada de domínio não deve se preocupar com menus.

Ela também não deve se preocupar com a forma como os dados serão salvos.

Ela representa as informações e relações importantes do sistema.

Camada de infraestrutura​

A camada de infraestrutura cuida dos detalhes técnicos que dão suporte ao sistema.

No momento atual do projeto, o armazenamento é feito em arrays.

Por isso, a pasta Infraestrutura contém repositórios como:

  • RepositorioEquipamento;
  • RepositorioChamado.

Um repositório é uma classe responsável por guardar, recuperar e alterar registros.

No projeto, o RepositorioEquipamento mantém um array de equipamentos e oferece operações como:

  • cadastrar;
  • editar;
  • excluir;
  • selecionar todos.

Um exemplo simplificado seria:

public class RepositorioEquipamento
{
    private Equipamento[] equipamentosSalvos = new Equipamento[100];

    public void Cadastrar(Equipamento novoEquipamento)
    {
        // guarda o equipamento em uma posição livre do array
    }

    public Equipamento[] SelecionarTodos()
    {
        return equipamentosSalvos;
    }
}

O restante do sistema não precisa conhecer todos os detalhes do array.

Ele apenas pede para o repositório cadastrar, editar, excluir ou selecionar registros.

Mais adiante, esse armazenamento poderia mudar para arquivos ou banco de dados.

Mesmo assim, a ideia da camada continuaria fazendo sentido.

O papel do Program.cs​

Depois da separação em camadas, o Program.cs deixa de concentrar tudo.

Ele passa a coordenar a aplicação.

Na branch v3 do projeto, o Program.cs cria os repositórios e as telas:

RepositorioEquipamento repositorioEquipamento = new RepositorioEquipamento();
RepositorioChamado repositorioChamado = new RepositorioChamado();

TelaPrincipal telaPrincipal = new TelaPrincipal();
TelaEquipamento telaEquipamento = new TelaEquipamento();
TelaChamado telaChamado = new TelaChamado();

Depois, ele conecta as telas aos repositórios que elas precisam usar.

Por exemplo, a tela de chamados precisa acessar:

  • o repositório de chamados, para cadastrar e listar chamados;
  • o repositório de equipamentos, para escolher o equipamento relacionado ao chamado.

Essa ligação aparece de forma parecida com isto:

telaChamado.repositorioChamado = repositorioChamado;
telaChamado.repositorioEquipamento = repositorioEquipamento;

Depois disso, o Program.cs controla o fluxo principal:

  • mostra o menu principal;
  • identifica se o usuário escolheu equipamentos ou chamados;
  • chama a tela correta;
  • executa a operação escolhida.

Ele ainda é importante.

Mas agora ele não precisa conter todos os detalhes de cada cadastro.

O fluxo entre as camadas​

Vamos acompanhar um cadastro de equipamento.

Primeiro, o usuário escolhe a opção de cadastrar equipamento.

Essa escolha passa pela camada de apresentação.

A TelaEquipamento pede os dados pelo console:

  • nome;
  • preço de aquisição;
  • data de fabricação.

Depois, ela cria um objeto do domínio:

Equipamento equipamento = new Equipamento();
equipamento.nome = nome;
equipamento.precoAquisicao = precoAquisicao;
equipamento.dataFabricacao = dataFabricacao;

Em seguida, ela envia esse objeto para a infraestrutura:

repositorioEquipamento.Cadastrar(equipamento);

O fluxo pode ser lido assim:

Usuário
  ↓
Apresentação
  ↓
Domínio
  ↓
Infraestrutura

Na prática:

Console
  ↓
TelaEquipamento
  ↓
Equipamento
  ↓
RepositorioEquipamento

Essa separação ajuda a enxergar o caminho da informação dentro do sistema.

Por que separar em camadas?​

Separar em camadas não é apenas uma questão de deixar as pastas bonitas.

A separação ajuda porque cada parte do código fica com uma responsabilidade menor.

A camada de apresentação cuida da interação com o usuário.

A camada de domínio representa os conceitos principais do problema.

A camada de infraestrutura cuida de como os dados são armazenados.

Com isso, fica mais fácil:

  • encontrar onde uma funcionalidade está implementada;
  • alterar o menu sem mexer no armazenamento;
  • alterar o armazenamento sem reescrever todas as telas;
  • reutilizar classes de domínio em outras partes do sistema;
  • evoluir o projeto aos poucos.

Também fica mais fácil para uma equipe trabalhar no mesmo projeto.

Um aluno pode estar ajustando a tela de equipamentos.

Outro pode estar melhorando o repositório.

Outro pode estar criando novas classes de domínio.

Como as responsabilidades estão separadas, o risco de conflito diminui.

Uma observação importante​

A arquitetura em camadas não resolve todos os problemas automaticamente.

Ela é uma forma de organizar o código.

Se uma classe da camada de apresentação começar a fazer muita regra de negócio, o problema apenas mudou de lugar.

Se o repositório começar a mostrar mensagens no console, a infraestrutura passou a depender da apresentação.

Por isso, ao criar ou alterar uma classe, faça sempre esta pergunta:

esta responsabilidade pertence mesmo a esta camada?

Essa pergunta simples ajuda a manter o projeto organizado.

Relação com encapsulamento​

Na aula anterior, vimos encapsulamento.

Encapsulamento protege os detalhes internos de uma classe.

Camadas aplicam uma ideia parecida em uma escala maior.

Em vez de proteger apenas os atributos de um objeto, protegemos também as responsabilidades de cada parte do sistema.

A tela não precisa saber como o array funciona.

O repositório não precisa saber como o menu é desenhado.

O domínio não precisa saber se o usuário está usando console, tela web ou qualquer outra interface.

Cada parte conhece apenas o necessário para cumprir seu papel.

Conclusão​

A arquitetura em 3 camadas ajuda a organizar aplicações que começam a crescer.

No projeto de gestão de equipamentos, a branch v3 separa o código em:

  • Apresentacao, para telas e interação com o usuário;
  • Dominio, para classes como Equipamento e Chamado;
  • Infraestrutura, para repositórios e armazenamento em memória.

Essa divisão deixa o sistema mais claro.

O código fica mais fácil de navegar, alterar e evoluir.

Esse é um passo importante entre escrever programas pequenos e começar a construir aplicações mais organizadas.
