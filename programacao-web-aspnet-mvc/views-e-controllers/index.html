Views e Controllers

O problema de responder a uma requisição​

Na aula anterior, vimos que o ASP.NET consegue criar um servidor web.

Também vimos que o método MapDefaultControllerRoute conecta URLs aos controllers.

Porém, ainda precisamos entender o que acontece depois que uma URL chega ao controller.

Quando um usuário acessa uma página, a aplicação precisa:

  • identificar qual código deve ser executado;
  • buscar ou receber os dados necessários;
  • montar uma resposta para o navegador.

No ASP.NET MVC, essa responsabilidade é dividida principalmente entre Controller e View.

O Controller coordena o fluxo da requisição.

A View monta o HTML que será exibido para o usuário.

Relembrando o MVC​

MVC é uma forma de organizar uma aplicação em três partes:

  • Model, que representa os dados e as regras do sistema;
  • View, que representa a interface exibida no navegador;
  • Controller, que recebe requisições e coordena as respostas.

Podemos visualizar o fluxo de uma página assim:

Navegador
   ↓ requisição
Controller
   ↓ consulta ou altera
Model e repositório
   ↓ dados
View
   ↓ HTML
Navegador

Essa separação não significa que as partes trabalham isoladamente.

O Controller pode enviar dados para a View.

A View pode enviar dados de um formulário para o Controller.

Cada parte apenas possui uma responsabilidade principal.

O Controller coordena o fluxo. A View apresenta os dados. O Model representa informações importantes do sistema.

Onde estão os Controllers e as Views?​

No repositório controle-de-medicamentos-2026, a aplicação web fica no projeto ControleDeMedicamentos.WebApp.

Na versão v7, encontramos uma estrutura parecida com esta:

ControleDeMedicamentos.WebApp/
├── ModuloFornecedores/
│   ├── Fornecedor.cs
│   └── FornecedorController.cs
├── Views/
│   ├── Fornecedor/
│   │   ├── Cadastrar.cshtml
│   │   ├── Editar.cshtml
│   │   ├── Excluir.cshtml
│   │   └── Listar.cshtml
│   └── Home/
│       └── Index.cshtml
└── Program.cs

O projeto agrupa o controller do fornecedor dentro do módulo ModuloFornecedores.

As Views ficam dentro da pasta Views.

Essa organização permite encontrar com facilidade os arquivos relacionados a cada recurso.

O que é um Controller?​

Um Controller é uma classe responsável por receber requisições HTTP e decidir qual resposta deve ser enviada.

Ele normalmente:

  • recebe dados da URL ou de um formulário;
  • chama um repositório ou serviço;
  • verifica se uma operação foi possível;
  • envia dados para uma View;
  • redireciona o usuário para outra action;
  • retorna respostas como NotFound.

No ASP.NET MVC, o nome do controller normalmente termina com Controller.

Por exemplo:

public sealed class FornecedorController : Controller
{
}

O sufixo Controller faz parte da convenção do ASP.NET MVC.

O nome lógico desse controller é Fornecedor.

O que é uma Action?​

Uma action é um método público de um controller que pode ser executado em resposta a uma requisição.

No controller de fornecedores, existem actions como:

[HttpGet]
public ActionResult Listar()
{
    // código executado ao abrir a lista
}

O método Listar é uma action.

O atributo [HttpGet] indica que ela responde a uma requisição do tipo GET.

Esse é o tipo de requisição normalmente usado quando o usuário abre uma página.

Uma action pode retornar diferentes respostas.

No exemplo do projeto, ela retorna uma View:

return View(fornecedores);

Também pode retornar um redirecionamento:

return RedirectToAction(nameof(Listar));

Ou informar que um registro não foi encontrado:

return NotFound();

O tipo ActionResult permite que uma action retorne essas diferentes respostas.

Como a rota encontra uma action?​

No Program.cs da versão v7, o MVC é habilitado com:

builder.Services.AddControllersWithViews();

Depois, a rota padrão é registrada com:

app.MapDefaultControllerRoute();

Essa rota segue uma convenção semelhante a:

/{controller=Home}/{action=Index}/{id?}

Isso significa que uma URL pode informar:

  • o nome do controller;
  • o nome da action;
  • um identificador opcional.

Por exemplo:

/Fornecedor/Listar

é direcionada para:

FornecedorController.Listar()

Já a URL:

/Fornecedor/Editar/3

é direcionada para a action Editar, recebendo o valor 3 no parâmetro id.

[HttpGet]
public ActionResult Editar(int id)
{
    // id recebe o valor 3
}

A rota transforma partes da URL em informações que podem ser recebidas pelos parâmetros da action.

Exibindo dados com uma View​

Uma View é um arquivo que contém o HTML da página.

No ASP.NET MVC, as Views costumam usar a sintaxe Razor.

Razor permite misturar HTML com C#.

No projeto de exemplo, a View da listagem está em:

Views/Fornecedor/Listar.cshtml

A action Listar procura essa View quando executa:

return View(fornecedores);

O ASP.NET procura uma View com o mesmo nome da action dentro da pasta relacionada ao controller.

Neste caso:

FornecedorController.Listar()
            ↓
Views/Fornecedor/Listar.cshtml

Enviando um Model para a View​

Antes de retornar a View, o controller busca os fornecedores no repositório:

[HttpGet]
public ActionResult Listar()
{
    List<Fornecedor> fornecedores = repositorio.SelecionarTodos();

    return View(fornecedores);
}

O objeto enviado dentro de View(fornecedores) é chamado de Model da View.

Na primeira linha da View, informamos qual tipo de dado ela espera receber:

@using ControleDeMedicamentos.WebApp.ModuloFornecedores

@model List<Fornecedor>

Agora, a variável Model representa uma lista de fornecedores.

A View usa essa lista para construir as linhas da tabela:

<tbody>
    @foreach (Fornecedor f in Model)
    {
        <tr>
            <td>@f.Id</td>
            <td>@f.Nome</td>
            <td>@f.Telefone</td>
            <td>@f.Cnpj</td>
        </tr>
    }
</tbody>

O @ indica que estamos saindo do HTML para executar uma expressão Razor ou C#.

Por exemplo:

  • @f.Nome escreve o nome do fornecedor;
  • @f.Id escreve o identificador;
  • @foreach repete um trecho de HTML para cada item.

O resultado enviado ao navegador é HTML.

O navegador não recebe o C# do Razor.

Exibindo uma lista completa​

A View Listar.cshtml usa uma tabela para mostrar os fornecedores cadastrados.

O trecho abaixo cria o cabeçalho:

<table>
    <thead>
        <tr>
            <th>Id</th>
            <th>Nome</th>
            <th>Telefone</th>
            <th>CNPJ</th>
            <th>Ações</th>
        </tr>
    </thead>
</table>

Depois, o foreach cria uma linha para cada fornecedor.

Esse é um exemplo simples da responsabilidade de uma View:

receber dados prontos e transformá-los em uma estrutura visual para o usuário.

A View não precisa saber como os dados foram lidos do arquivo.

Essa tarefa pertence ao repositório, chamado pelo controller.

Abrindo uma página de cadastro​

O cadastro possui uma action para exibir o formulário:

[HttpGet]
public ActionResult Cadastrar()
{
    return View();
}

Como nenhum Model foi enviado, essa View não precisa declarar um @model.

O arquivo correspondente é:

Views/Fornecedor/Cadastrar.cshtml

Nele, encontramos um formulário HTML:

<form action="Cadastrar" method="post">
    <div>
        <label for="nome">Nome</label>
        <input id="nome" name="nome" type="text">
    </div>

    <div>
        <label for="telefone">Telefone</label>
        <input id="telefone" name="telefone" type="text">
    </div>

    <div>
        <label for="cnpj">CNPJ</label>
        <input id="cnpj" name="cnpj" type="text">
    </div>

    <button type="submit">Cadastrar</button>
</form>

O atributo method="post" informa que o formulário enviará uma requisição POST.

Os valores digitados serão enviados pelos nomes dos campos:

  • nome;
  • telefone;
  • cnpj.

Recebendo dados de um formulário​

O mesmo controller possui outra action chamada Cadastrar:

[HttpPost]
public ActionResult Cadastrar(string nome, string telefone, string cnpj)
{
    Fornecedor fornecedor = new Fornecedor(nome, telefone, cnpj);

    repositorio.Cadastrar(fornecedor);

    return RedirectToAction(nameof(Listar));
}

Apesar de ter o mesmo nome, essa action é diferente da action que exibe o formulário.

Uma responde a GET.

A outra responde a POST.

O ASP.NET identifica os valores do formulário e associa cada um ao parâmetro correspondente.

Depois, o controller:

  1. cria um objeto Fornecedor;
  2. envia o objeto para o repositório;
  3. redireciona o usuário para a lista.

O redirecionamento é feito com:

return RedirectToAction(nameof(Listar));

Assim, após cadastrar, o usuário volta para a página de listagem.

A diferença entre GET e POST​

Em um formulário, normalmente usamos dois momentos:

GET para exibir​

O GET abre uma página ou busca informações.

Exemplo:

[HttpGet]
public ActionResult Cadastrar()
{
    return View();
}

POST para enviar​

O POST envia dados para uma operação que pode alterar o sistema.

Exemplo:

[HttpPost]
public ActionResult Cadastrar(string nome, string telefone, string cnpj)
{
    // cadastra um fornecedor
}

Podemos resumir o cadastro assim:

GET /Fornecedor/Cadastrar
   ↓
Exibe o formulário
   ↓ usuário preenche
POST /Fornecedor/Cadastrar
   ↓
Salva o fornecedor
   ↓
Redireciona para /Fornecedor/Listar

Essa separação deixa claro quando a aplicação está apenas exibindo uma tela e quando está processando dados enviados pelo usuário.

Editando um registro​

A edição combina os mesmos conceitos com o uso de um identificador.

Primeiro, o controller busca o fornecedor pelo id recebido na URL:

[HttpGet]
public ActionResult Editar(int id)
{
    Fornecedor? fornecedor = repositorio.SelecionarPorId(id);

    if (fornecedor == null)
        return NotFound();

    return View(fornecedor);
}

Se o registro não existir, a aplicação retorna NotFound().

Se existir, o objeto é enviado para a View.

A View Editar.cshtml declara que espera receber um único fornecedor:

@using ControleDeMedicamentos.WebApp.ModuloFornecedores

@model Fornecedor;

Com isso, pode preencher os campos usando o objeto Model:

<input id="nome" name="nome" type="text" value="@Model.Nome">
<input id="telefone" name="telefone" type="text" value="@Model.Telefone">
<input id="cnpj" name="cnpj" type="text" value="@Model.Cnpj">

O usuário recebe um formulário já preenchido.

Quando confirma a edição, o formulário envia os novos valores para a action POST:

[HttpPost]
public ActionResult Editar(int id, string nome, string telefone, string cnpj)
{
    Fornecedor fornecedorAtualizado = new Fornecedor(nome, telefone, cnpj);

    bool conseguiuEditar = repositorio.Editar(id, fornecedorAtualizado);

    if (!conseguiuEditar)
        return NotFound();

    return RedirectToAction(nameof(Listar));
}

O id identifica qual fornecedor deve ser alterado.

Os demais parâmetros representam os novos valores.

Controller não é a View​

É importante não misturar as responsabilidades.

O controller não deve montar HTML usando Console.WriteLine ou grandes strings.

Também não deve conter todo o código visual da página.

A View não deve abrir arquivos diretamente nem decidir como o fornecedor será salvo.

Uma divisão adequada fica parecida com esta:

FornecedorController
   - recebe a requisição
   - chama o repositório
   - escolhe a resposta

Listar.cshtml
   - recebe a lista
   - monta a tabela HTML
   - cria links e formulários

RepositorioFornecedorEmArquivo
   - salva e recupera fornecedores

Essa divisão torna cada arquivo mais simples de entender.

Fluxo completo da listagem​

Vamos acompanhar o acesso à página de fornecedores.

O usuário abre:

/Fornecedor/Listar

O fluxo é:

  1. O navegador envia uma requisição GET.
  2. A rota identifica FornecedorController e a action Listar.
  3. O controller chama repositorio.SelecionarTodos().
  4. O repositório retorna uma lista de fornecedores.
  5. O controller chama View(fornecedores).
  6. A View percorre a lista com foreach.
  7. O Razor gera HTML.
  8. O servidor envia o HTML para o navegador.

Esse caminho pode ser representado assim:

GET /Fornecedor/Listar
        ↓
FornecedorController.Listar
        ↓
RepositorioFornecedorEmArquivo
        ↓
List<Fornecedor>
        ↓
Views/Fornecedor/Listar.cshtml
        ↓
HTML no navegador

Observações sobre o projeto de exemplo​

Na versão v7, o controller cria o repositório dentro do próprio construtor:

public FornecedorController()
{
    ContextoJson contextoJson = new ContextoJson();

    contextoJson.Carregar();

    repositorio = new RepositorioFornecedorEmArquivo(contextoJson);
}

Esse código permite que o exemplo funcione e mostra a ligação entre controller e persistência.

Em aplicações maiores, essa dependência pode ser configurada pela injeção de dependência.

Esse assunto será aprofundado mais adiante.

Por enquanto, é suficiente perceber que o controller precisa de um objeto capaz de buscar e alterar fornecedores.

Conclusão​

O Controller recebe requisições e coordena o fluxo da aplicação.

Uma action é um método do controller que responde a uma requisição.

O atributo [HttpGet] costuma ser usado para exibir páginas.

O atributo [HttpPost] costuma ser usado para receber dados de formulários.

A View é um arquivo .cshtml que usa Razor para gerar HTML.

No projeto controle-de-medicamentos-2026, o controller de fornecedores conecta:

  • a rota /Fornecedor/Listar à action Listar;
  • a action ao repositório de fornecedores;
  • a lista retornada à View Views/Fornecedor/Listar.cshtml.

Quando essas responsabilidades estão separadas, o código fica mais fácil de ler e evoluir.

Na próxima etapa, podemos melhorar os formulários usando recursos próprios do ASP.NET MVC para preencher campos, validar dados e exibir mensagens de erro.
